# The player

Purpose: a player for music you already have on a server. It is a **Tauri 2** application —
Rust core, the operating system's own WebView, no bundled Chromium and no Electron — that
speaks **Subsonic / OpenSubsonic** to whatever server a person points it at. It is a client
and only a client: it never runs this app's Python backend, it ships no acquisition code, and
it does not need the desktop host in `desktop/`. The shells are separately distributable and
share only the stylesheet: `player/ui/src/app.css` imports `web/styles/app.css` at build time,
so a visual change belongs in `web/styles/` and never in the player.

Card: **PLAYER-001** — the shell and its connect screen. Everything past the handshake has a
card of its own, listed at the end.

> **Current build (2026-11-14).** The player is `player/ui/`: Svelte 5 + TypeScript + Vite,
> built to `player/ui/dist`, and `tauri.conf.json` points at it. It talks to the server through
> the typed Subsonic client in `player/ui/src/lib/subsonic/`; it does not load `web/index.html`
> and it names none of this server's `/api/…` routes except the two social reads described below.
> The earlier host-shell approach — an
> `assemble.mjs` that copied `web/` into a gitignored `player/www/`, a `player/shell/` of
> classic scripts, and an offline-download feature — is **deleted**, not merely unused. `P4` in
> the plan removed it after `tauri.conf.json` stopped pointing at it.

    src/lib/hardly/     the one non-Subsonic surface: the social capability probe, inert

                        QueuePanel, Subtitle, LyricsOverlay

  src-tauri/
    Cargo.toml          tauri 2, one library crate for desktop/iOS/Android
    build.rs            tauri_build
    tauri.conf.json     the window, ../ui/dist as the front end, desktop + iOS + Android bundle

    src/lib.rs          the builder, the managed state, every command
    src/main.rs         the desktop binary
    src/accounts.rs      the keychain, or an in-memory vault that says so
    src/subsonic.rs      the commands that know the address and the credential

`player/ui/dist` is generated by Vite and is the only thing the window loads. There is no
second tree.

## What the player contains, and what it must not

The player's contents are a property of the **build**, and `tests/test_player_store_safe.py`
asserts them over `player/ui/dist` — the tree the window actually loads — rather than over a
list in a script, because a list is a promise and a build is evidence. See
[player/store-safe.md](player/store-safe.md).

Present, because a client needs them: the Subsonic client (auth, transport, normalisation,
error codes), the library surfaces (albums, artists, playlists, search, stars), playback and
Up Next, lyrics, and optionally this server's social feed once PLAYER-006 lands.

Absent, by construction: **every `/api/…` route this server registers**. A player that spoke
them would be a second client of one implementation; it speaks `/rest/…` instead. Also absent:
the acquisition module, the download queue, source matching, the offline cache, and the
provider browser. None of these is hidden behind a flag — the modules do not exist.

Two consequences worth stating plainly:

* **The exclusion is checked, not remembered.** The test derives the forbidden names from
  `api/v1.py`'s own route table and from `web/js/repo-discovery.js` at test time, so a new
  server route joins the assertion without anyone updating a list. It has a negative control:
  it plants a private route and a machinery token in a copy of the build and requires the audit
  to report them.
* **It cannot prove a runtime-built URL.** A player script could concatenate a route at
  runtime and no static audit would see it. That limit is stated in `store-safe.md` rather than
  left implied.

## Running it

Requirements beyond this repository: Rust (stable), the Tauri 2 CLI
(`cargo install tauri-cli --version "^2"`), and the WebView development packages for the
platform — on Linux `webkit2gtk-4.1`, `gtk+-3.0` and `libsoup-3.0`, per Tauri's prerequisites
page.

```sh
# the player's own build (also run by Tauri's beforeBuildCommand)
cd player/ui && npm install && npm run build

# development: the Vite dev server starts first, then the window opens
cd player/src-tauri
cargo tauri dev

# a desktop build (appimage/deb on Linux, .app on macOS, .msi on Windows)
cargo tauri build
```

`beforeDevCommand`/`beforeBuildCommand` in `tauri.conf.json` call `npm --prefix ui run dev` /
`run build`, so the front end is not a step a person can forget (Tauri runs them from
`player/`). To look at the player without Rust, `cd player/ui && npm run dev` and open
`http://localhost:5179`; `?preview=compact|fullscreen|queue` renders one surface on its own for
the parity harness, and `node tools/parity.cjs` grades all of them against the stored
baselines.

`vite.config.ts` sets `base: "./"` because the shell serves `dist/` over Tauri's asset
protocol — there is no server to resolve an absolute path, on any of the three platforms.

`security.csp` is set (2026-11-17), one policy for all three platforms:

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: http: https:; media-src 'self' data: blob: http: https:;
connect-src 'self' ipc: http://ipc.localhost; font-src 'self' data:;
object-src 'none'; frame-src 'none'; base-uri 'none'; form-action 'none'
```

Each allowance has a reason, and the reasons are why the policy is not tighter:

- **`img-src`/`media-src` need `http:`/`https:`.** A cover and a stream are URLs the native side
  hands to an `<img>` and an `<audio>` element. A media element cannot carry headers, so its
  authentication travels in the query string and the page itself must be allowed to fetch the
  URL. The host is the account's own server, but a policy cannot name a host a person types.
- **`style-src` needs `'unsafe-inline'`, for attributes only.** Sheets are one bundled file, but
  several components set `style=` (the queue slot's position, the record's travel, the volume's
  `--vol`). `style-src-attr` would say this more precisely; it is ignored by WebKit before 15.4,
  which would then block those attributes outright, so the older spelling stays.
- **`script-src 'self'`, with no `'unsafe-inline'`.** That is the point of the policy: the page
  runs the bundle and nothing a server, a cover or a lyric could smuggle in.
- **`connect-src` stays at the asset origin and IPC.** The page names endpoints and never URLs;
  Rust resolves the host and the credential. The two reads outside `/rest` — the capability
  document and the feed — go through the native side for the same reason
  (`lib/hardly/native.ts` → `subsonic_public`, `docs/player/social.md`), which is what keeps this
  policy at IPC instead of widening it to `http: https:`. The only page-side `fetch` left is the
  no-native fallback in `transport.ts`, which exists for shells older than the native transport
  and is refused here by design.

Measured on the Linux build against a stub OpenSubsonic server: connect, album wall with real
covers and the drawn fallback, artists, playlists, playlist detail, artist detail, album detail,
a row's queue action, and the full player (record, label artwork, seek, volume) all render with
no CSP refusal in the app log. Search (`search3` → one song), paging (a full 50-row page shows
"Show more"; the short second page appends and the button goes) and the star toggle (the heart
sends `star`, then `unstar`, and the pressed state follows) were walked the same way. `media-src` was not exercised — no playback was run on the
workstation — so a stream under this policy is unproven until it plays on the device. The policy
is baked into the packaged binary: the string is present in the arm64 IPA's executable, so the
shipped app carries it rather than the source only.

### iOS and Android

Tauri generates the platform projects; they are **not** committed (`gen/apple`,
`gen/android` are gitignored, and `src-tauri/gen/` is what the CLI produces):

```sh
cd player/src-tauri
cargo tauri icon path/to/1024.png     # icons are not in the tree yet
cargo tauri ios init                  # once: writes gen/apple
cargo tauri android init              # once: writes gen/android
cargo tauri ios dev                   # or: cargo tauri android dev
```

`bundle.iOS.minimumSystemVersion` is 13.0 and `bundle.android.minSdkVersion` is 24; those are
declared in `tauri.conf.json` and unverified here (see below). The window URL is `index.html`,
the same relative page on all three platforms, so no platform gets its own front end.

## The connect screen

When no server is configured the window shows one card: server address, username, password
(`src/components/Connect.svelte`). It calls
`<server>/rest/ping.view?u=…&p=…&v=1.16.1&c=hardlylistening-player&f=json` and reads the reply
as the protocol defines it:

* a **`subsonic-response` with `status: "ok"`** is a success, and the screen reports the
  server's `type`, `serverVersion` and whether it is `openSubsonic`;
* an **`error` object** is reported by its code — 40 is wrong credentials, 30 is a protocol
  version the server will not speak, 10 a missing parameter — with the server's own message
  appended when it adds something;
* **anything else** (an HTML login page, a proxy error, JSON without the envelope) is refused
  as "answered, but not as a Subsonic server", because a person needs to know which of those
  happened.

The address is normalised only where normalising cannot be wrong: trailing slashes are
dropped, and a pasted `/rest` suffix is named rather than doubled. A missing scheme is
refused rather than guessed (`http` versus `https` is the person's choice).

**Credentials go to the OS keychain** (`src-tauri/src/accounts.rs`: Keychain, Credential
Manager, Secret Service). A platform with no keychain backend keeps the secret in memory and
says so, rather than writing a password to disk — and the screen follows the store it has:
`accounts_mode` is asked at startup and `accounts_put` answers with the mode the write really
used, so the fine print under Connect names the keychain only when a keychain answered. The page holds an account's public record —
id, address, username, label — and asks Rust for the secret when a request needs it. The
password crosses to the server as Subsonic's plain `p=` parameter, so the address should be
`https://`; token auth (`t`/`s`, md5) is supported by the client but not used for the bind.
`docs/player/accounts.md` and `docs/player/transport.md` are the two documents for this.

## A screen that has nothing to show

A player is asked what it is by the states that are not the happy path. `Shell.svelte` and
`Connect.svelte` answer three of them in words rather than in blanks, and one of them is a
control:

* **An empty library, and an empty thing inside it.** Each wall says what is missing — "This
  server has no albums yet", no artists, no playlists, "Nothing is starred on this server yet",
  "No results for "zzz"." for a search that matched nothing — and so does each detail view: "This
  album has no songs on this server", "This artist has no albums here", "This playlist is
  empty". A Play button over nothing is disabled rather than inert, because a button that looks
  live and does nothing is the worse answer. A failure is not an empty library, so the message is
  suppressed while `library.error` is set; otherwise a dead connection would read as a server with
  no music.
* **A search says what it searched for.** The box can be edited after a search without running it
  again, so the term is not read back off the input: `search()` records it (`lastQuery`, trimmed)
  and the results carry a heading — "Results for <term>", the term in its own case, because it is
  what somebody typed and not a section label. An empty result names it too, so "nothing matched"
  and "the search never ran" stop looking the same.
* **A load that failed.** `albumsDone` is set on failure too, so the "Show more" button vanishes
  and there would be nothing left to press. The failure carries its own **Try again**, which
  reloads the open tab.
* **A stream that failed.** `player.error` was set by three paths — the engine's own error event
  ("This track could not be played"), the native engine, the failed star in `toggleLike` — and
  nothing drew it, so the sign of a dead stream was a Play button that did nothing. The line is
  now drawn where the person is looking: above the content in `Shell.svelte`, and under the title
  in `FullPlayer.svelte` for the case where the player is the whole screen. It is absent, and
  costs no pixel, when there is nothing to say.
* **A failure sentence.** The Rust transport now classifies its own error
  (`subsonic.rs::transport_reason`) instead of printing `reqwest`'s `Display`, because that
  `Display` ends in the request URL and Subsonic puts the credential in the query string (`u`
  plus `p`, or a salted `t`/`s`). What a person sees is "Could not reach <address> — the
  connection was refused" (or timed out / cut short / redirected); the address stays because it
  is the part they can check. `a_failure_sentence_never_repeats_the_url_the_credential_travels_in`
  builds the real URL, makes the real failing request and asserts the sentence carries no
  password, no query and none of `u=`, `p=`, `t=`, `s=`.
* **The web path's failure sentence.** The same line on the `fetch` transport printed the
  engine's own phrase — `Could not reach http://127.0.0.1:9 — Failed to fetch` — which names a
  browser internal, reads as a defect in this client, and is worded differently on each engine
  ("NetworkError when attempting to fetch resource." on Firefox, "Load failed" on WebKit). Every
  one of those phrases means the same checkable thing, and that is what the line now says:
  *the request got no answer*. A sentence this list does not contain is left as the engine said
  it, because then it is specific. `transport.test.ts` feeds all four engines' wording and
  asserts none of them reaches the message, that a CORS sentence still does, and that the
  address stays.

The album grid is sized from the host's density variable (`--song-cols`, 2 on a phone, 4 on a
desktop). The player has no density control, so it takes those defaults explicitly; without them
the grid fell back to 4 columns at any width and a 390 px window showed every title as "N…".
Its phone layout was walked in a 390×844 window, not resized after the fact.

**Names come from the server, and the host's base sheet assumes they are short.** `base.css` sets
`white-space: nowrap` on every `button`, which is right for a chip and wrong for an artist row:
a long name ran past the card and pushed the album count off the edge, and on the connect screen
an address with a long path (no spaces, so no break opportunity) set the width of the whole card
and made the screen scroll sideways. The row's name now truncates with an ellipsis and keeps its
column while the count keeps its own; the saved-server label wraps (`overflow-wrap: anywhere`)
and the `×` stays where the thumb expects it. Walked at 390×844 with a 130-character artist and a
server address carrying a long path.

The bar's second line had the same problem in a nastier form. `#player .psub .psub-a` is
`flex: 0 0 auto; max-width: 100%`, so a long artist took the whole line, the separator stayed
where it was, and the release link was squeezed to zero width — a line that ended in a floating
"·", plus a link that Tab could still reach while nothing was there to see. The artist now caps at
the 62% the fullscreen player's subtitle has always used, so both names keep room and both
truncate. Measured at 390×844 with a 130-character artist: two 88 px halves and a 12 px
separator, where the second half used to be 0.

**The reading never outlives its words.** Skipping tracks with the words open left the overlay
in place while the store cleared them, so a track the server had nothing for showed an empty
panel over the disc — no lines, no status, only a close button, and no way to tell that from a
server that was slow. The host hides its overlay on `loadstart` for the same reason: the
reading belongs to the track. `#present` now closes it with the words, and the pill dims
because there is nothing to read until this track's own answer arrives. Measured in the app's
engine at 390×844 (`on` → `` on a skip to a words-less track) and walked in the built binary.

**The words follow the clock.** OpenSubsonic times lyrics in milliseconds (`line.start`,
`offset`); every clock in this app — `audio.currentTime`, the engine's `time` event, the
scrubber — is in seconds. The two were compared as they arrived, so a line starting at four
seconds read as four thousand: the highlight sat on the first line of every song and never
moved, which is the one thing a synced reading exists to do. The conversion now happens at the
boundary, in `SubsonicClient.lyrics`, and nowhere else. Measured in the app's engine at
390×844 (10.8 s into a 180 s track → the third line, 90 s → the fourth) and walked in the
built binary by scrubbing: 0:06 highlights the line that starts at 0:04, 1:30 the last one,
with the reading scrolling to follow.

**A control the engine cannot honour is not drawn.** The reading's tools row carried a
Fullscreen button; on a desktop WebView it takes the window, which is why it is there. iOS can
put a `<video>` fullscreen and nothing else, and WKWebView follows Safari there, so on the phone
— the surface this player exists for — it was a button that could not move anything, in a
fullscreen view that was already fullscreen. `supportsElementFullscreen()` decides, accepting the
web-prefixed spelling iPadOS has carried from 12 onwards, and the button is only drawn when the
answer is yes. Its four cases are unit-tested, because a missing button is not something a
screenshot of a working engine can show.

**"Has words" now looks like it.** `#player-full .pf-lyrics #pflyrics` carries two ids and a
class, so the one-id `#pflyrics.lyrics-ready` beside it in `lyrics.css` never won: the accent that
says "this track has something to read" was never painted, and the only difference between a
track with words and one without was the dimming of the disabled state. The ready rule is now
spelled with the same weight. Measured at 1200×860: `rgb(88, 211, 168)` when the server answered
with words, and the disabled track still reads dim (`opacity: .45`), because the disabled rule
comes later at equal weight.

**The queue and the words are one square.** The queue slot is drawn over the disc column and
the lyrics overlay inside it, and nothing stopped both from being open: the queue's own rows
printed straight through the second line of the song ("A starred song Alex Ross" across it), and
the words' tools row sat underneath the queue's header. Opening either now closes the other,
from the page that owns the queue's state, and closing the fullscreen player closes the reading
with it. Measured in the app's engine at 390×844 both ways round — queue open then Lyrics leaves
the panel closed (`in-full`, no `queue-open`) and the words on; Lyrics then the queue button
leaves the words off — then walked in the built binary: one surface, one reading.

**Signing out asks.** The server chip in the header is the only control that is not a
destination, and one tap used to end the session. It now becomes "Sign out?" (red) on the first
tap, does the thing on the second, and returns to the address after five seconds or on Escape.
The record and its keychain secret survive, which is why the connect screen can offer the
account straight back — a mis-tap costs one tap, not a lost library.

**And it takes the queue with it.** The library walls were let go on sign-out; the player was
not. A queue belongs to the server that issued its ids, so after signing out of one server and
in to another the compact player still held the old song, and the red "This track could not be
played" from that old session sat over a library that had just loaded perfectly — a verdict on
the new server that it had done nothing to earn. `Session.signOut()` now calls
`PlayerStore.detach()`, which stops the engine, hands it no source, and clears the queue, the
playhead, the cover, the words, the star and the failure line. Walked at 390×844: play a track
that the stub refuses, sign out, reconnect — the shell comes back clean.

**The connect screen remembers.** Every record outlives a sign-out, so the card lists the saved
servers as rows (label and address, one tap to reconnect, no password — the keychain still has
it) and prefills the address and username of the newest one for the case where the secret is
gone.

**A saved server can be forgotten.** The list could only grow, so a typo that once pinged — or a
machine that is gone — stayed there for good and failed on every tap. Each row now carries a
`×` at its fixed width, and like the sign-out chip it asks: the first tap becomes "Forget?", the
second removes the record, its keychain entry and its native binding, and five seconds or Escape
puts the `×` back. `Session.forget()` already did all of that; nothing had ever called it.

**A list of songs draws its own cells.** The host row is a file manager's row — cover, title,
artist, album, duration, download pair, mark — and the player's row has five cells instead:
index, title, artist, duration, and the queue button. Naming the columns was not enough. The
host's *player* list re-places the same cells by area (`44px 1fr auto`, `"art st more"`) because
its row carries a cover and a "more" menu, and it switches the index and the duration off, so
every list of songs in the player drew with an empty cover-sized hole at its left and neither an
index nor a duration: a row that read as a thumbnail that had failed to load. The component now
clears the areas and switches those two cells back on. On a phone the artist column goes, because
the title and the duration are what a row is for, and the queue button keeps its 30 px target.
Measured in the app's own engine at 390×844 and 1200×860, then walked in the built binary: index,
title, artist (desktop), duration and `+` in that order, with no dead space.

**And the list says which song that is.** The host marks a playing tile with a chip on its cover
— `.nowbars`, absolute, 24 px, a dark plate with an accent border — and a list row with bars
inline in its index cell. The player had one mark and put it in the wrong place: `TrackList`
carried the tile chip inside `.idx`, and `.songrow` is positioned, so it anchored to the row's
bottom-right corner and landed on the queue `+`, which then read as a covered button while the
index column sat empty. The row now draws the glyph statically inside `.idx`, the same placement
the host's own list row uses. Measured at 390×844: the index cell at x=51 holds the bars and the
`+` at x=322 is unobstructed. The album wall had no mark at all, so the docked bar named a song
and no tile owned it; `AlbumCard` gained the host's `playing` state and its corner chip, wired at
all four call sites from `player.track?.albumId === album.id`, with a scoped 10 px glyph because
the card's 34 px type overflowed the 24 px box. Measured: exactly one `.acard.playing` with a
24×24 chip on a 62-card albums wall and on a 31-card artist wall.

**The queue holds what will play, and it may hold one song twice.** Two defects lived there. The
host reveals its per-row Remove panel with a horizontal swipe; this client carries no swipe
controller, so the 92 px red panel stayed parked just inside each row's clipped edge and every
queued song wore a red sliver — the error colour on rows that were fine. The row now ends in a
`×` of its own, a 32 px target that a thumb can hit, calling the same `removeUpNext(position)`;
before it, "Clear queue" was the only removal that worked. The list was also keyed by the song's
id, which is not unique in a queue: queueing a song that was already up next queued it twice, the
heading counted four while two rows were drawn, and the two invisible songs still played. The
same key sat on `TrackList`, where a playlist is allowed to name one song twice. Both lists are
keyed by position now. Walked at 1200×860 and 390×844 with a duplicated queue and a playlist
containing one song twice.

**"Queue next" puts the song in front of the next one, not in its place.** The store keeps the
play order as a second list of queue positions, and the insert shifted every entry at or after
the insertion point — but it decided which entries were its own by comparing their values, so an
old entry that landed on one of the new numbers kept the old position. With `a` playing and the
queue `a b c`, one `+` left the order reading `a x x c`: the song that was going to play next was
no longer in the list, the added song was drawn twice, and the press after it played `x` again.
The order is shifted first and the new positions spliced in after; a store case pins queue
`a x b c` and up next `x b c` (the earlier one passed only because it queued the song already
playing). Walked at 390×844 against the stub: queueing track 3 from the album drew Up next
`track 3, track 2, track 3`, and Next played track 3.

**The queue's remove button did the opposite of its label on a keyboard.** The row is a
`role="button"` that plays its song on Enter or Space, and the `×` sits inside it, so the row's
`keydown` handler saw every key pressed on the button — and because it also called
`preventDefault` (which is what stops Space scrolling the page), the browser never got to activate
the button at all. One keystroke on "Remove Album 1 track 3 from the queue" played track 3 and left
it exactly where it was. The handler now ignores events that came from a child, so the row keeps
its Enter/Space and the button keeps its own. Measured at 390×844 with three songs queued and track
1 playing: Enter on the second row's `×` left Up next at one row with track 1 still playing
(previously: Up next 0, playing track 3), Space the same, and Enter on the row itself still plays
its song.

Removing a row also took the focus with it: the button that had focus was inside the row that
disappeared, so the browser dropped focus to `body` and the next Tab started again from the top of
the page, outside the sheet. The host refocuses the same control after a queue edit; here that is
whichever `×` took the removed row's place, the one above it when the last row went, and the
sheet's own close button once nothing is left to remove. Measured: focus lands on the next `×`
(390×844), and after emptying the queue on `.pq-close`, with the current track unchanged
throughout.

**The same capture, on the two other controls that sit inside a row.** The album list's `+`
("Queue next") is a button inside the song row, and the docked bar's artist and release links are
anchors inside the meta block that opens the fullscreen player — both rows claim Enter and Space
and both called `preventDefault`, so a keyboard could not use either control: Enter on `+` played
that song (with track 1 on, Up next went to 0 and the bar named track 3), and Enter on the artist
link opened the fullscreen player instead of the artist. Both handlers now ignore events raised
inside a child, which leaves the accessible path for each control where the host puts it. Measured
at 390×844: Enter on row 3's `+` plays nothing new — track 1 keeps playing and Up next reads
`track 3, track 2, track 3` — Enter on the bar's artist link opens the artist wall (31 cards, no
rows), Enter on the release link opens the album's three songs, and Enter on the row itself still
plays row 3.

**Up next can be reordered, and the reason it could not be was one field.** The host's queue row
carries the order's keyboard path — Alt with Up/Down moves a row one place, Alt with Home/End sends
it to either end — and the player had no reorder at all. `moveUpNext(from, to)` writes `#order`
only: the queue keeps every song and the playhead is a position in the order that is never crossed,
so a reorder cannot touch the current audio (and on a queue-owning player `#pushQueue` hands over
the new order, whose contract keeps the item that is playing). Adding it found the defect
underneath: `#order` was a plain private field, and every earlier edit changed it *alongside*
`queue`, so the view was redrawn by the queue's change rather than the order's. The first edit that

**The queue survives a reload, and it comes back paused.** The saved copy is
`hl.player.queue.v1`: the song fields a row needs to be painted, the order, and the playhead,
filed under the address of the server that issued the ids — a song id is only a name on the
server that gave it out. Signing out writes an empty queue under that same address, so leaving
does not resurrect a list the person cleared. Nothing in the restore asks for bytes: no source is
resolved, the engine is not told to play, and `playing` stays false; only the first press is what
calls `server.source()` and starts it. That is a deliberate difference from the host page, whose
spec stores ids only (`docs/playback-queue-ui.md`) and restores a list with no current song: the
host has a queue drawer that stands on its own, while this client's queue lives inside the
fullscreen player, which only exists once there is a track — a restored list with no playhead
would be a queue nobody could reach. So the track comes back too, at 0:00 with its metadata
length on the clock, until playback replaces that with the engine's own reading.

An order that does not describe its queue exactly — a hole, a repeat, an index past the end — is
dropped rather than repaired, because a permutation that is not a permutation plays the wrong
song. A saved queue from another server is ignored for the same reason.

paints no ring, because `:focus-visible` stays false after a click. Safari does not focus a button on

**Value text: declared, and not measurable on this engine.** The record is a `role="slider"` over
0–1000 and the two seek bars are `<input type="range">` over the same span, so a reader was handed
"76" between a min of 0 and a max of 1000 — a number in units nobody chose, on the controls whose
whole job is to say where in the song you are. All four now carry `aria-valuetext` ("0:01 of 0:30",
and "85%" on the volume fader), derived from the same `shownPosition` the visible clock prints, so
the announcement and the clock cannot disagree; the docked bar's seek bar does the same from its own
`scrubAt`/`progress`.

The other half is the honest one. Headless Chromium 156 refuses `aria-valuetext` for sliders in the
accessibility tree, measured three ways: a `role="slider"` div carrying both `aria-valuenow` and
`aria-valuetext` reports `value: 54, type: "number"` with a `valuetext` property of `""`; the same
div with only `aria-valuetext` reports `value: 500`, the midpoint of its min and max; an
`<input type="range">` reports `valuetext: "54"`, its own number, ignoring the attribute. Playwright's
`ariaSnapshot` agrees — `slider "Seek": "76"`. On Chromium the change is therefore declarative and
alters nothing a screen reader hears. It is the right declaration for an engine that honours it, and
the player's engine is WKWebView, where `aria-valuetext` is specified and honoured; there is no AX
inspection path to WebKit in this checkout, so that half is **unverified** rather than claimed. The
shape the measurement would otherwise suggest — dropping `aria-valuenow` so the text wins — is
invalid on a range slider and was not taken.

## What is unverified, and why

The host is Bazzite (immutable), with **no `webkit2gtk-4.1`, `gtk+-3.0` or `libsoup-3.0`
development packages and no `cargo-tauri`**, so nothing is built on the host itself. Everything
that can be built is built inside the `huibuild` distrobox, which has those packages:

* `cargo build --release --features tauri/custom-protocol` links the container's WebKit, and
  the window opens under Xvfb on X11 with `GDK_BACKEND=x11 LIBGL_ALWAYS_SOFTWARE=1
  WEBKIT_DISABLE_COMPOSITING_MODE=1 WEBKIT_DISABLE_DMABUF_RENDERER=1`. Every surface in this
  document has been walked that way against a stub OpenSubsonic server, at 1200×860 and at
  390×844;
* `cargo test --release` — 35 cases, several of them socket-level, including a stub that answers
  `/rest/*` — and `rustfmt --check` accept the Rust tree;
* the front end builds (`vite build`), type-checks (`svelte-check`) and passes 181 vitest cases;
* the built tree is audited file by file by `tests/test_player_store_safe.py` (9 tests).

What no Linux build settles is the device: `gen/apple`/`gen/android` generation, a real WKWebView,
the platform keychain, App Transport Security, and the platform audio engine — `native_audio.rs`
compiles, but `PLATFORM_PLAYER_PRESENT` is `false`, so playback runs through the WebView's
`<audio>` element. The iOS product is built unsigned on a macOS runner from `codemagic.yaml`;
installing it needs a signature this repository does not carry.

The local half of that gap is now written down and checked rather than assumed: the recipe in
`codemagic.yaml` sets `NSAllowsLocalNetworking` on the built product and fails if the packaged
IPA lost it (`NSAppTransportSecurity` → `NSAllowsLocalNetworking: true`). The narrow key is the
right one — it covers unqualified names, `.local` and IP addresses and leaves every public host
under ATS, where `NSAllowsArbitraryLoads` would not. It matters for the two loads the WebView
makes itself, a cover in an `<img>` and a stream in an `<audio>`; the `subsonic_*` commands are
unaffected either way, because ATS governs the URL Loading System and `reqwest` is not part of
it. What no recipe can settle is the device run: whether a plain `http://` LAN server then
answers belongs to HL-220's half, with the IPA installed. The CORS gap this section used to
describe is closed for the other reason: the `subsonic_*` commands send the request from Rust,
so the server's origin policy stops mattering, and the secret never returns to the page. The one
value that still crosses is a stream URL; see `docs/player/transport.md`.

## Social, when the server has it

The feed is this app's own feature, not the protocol's, so `player/ui/src/lib/hardly/social.ts`
asks the server's capability document whether it exists at all: `GET /api/v1/capabilities`, a
named `features.social.activity`, and no required member session. The answer is one of four
states — `activity`, `members`, `no-activity`, `absent` — and every failure lands in `absent`
with a reason rather than as an empty feed. `Session.social()` is the seam; nothing draws a feed
yet, and the probe is inert. The states, the read's typed refusals and the store-safe exception
are in [player/social.md](player/social.md).
